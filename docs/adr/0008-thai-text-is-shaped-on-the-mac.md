# ภาษาไทยถูกประกอบร่างบน Mac firmware แค่วาด glyph ที่ถูกเลือกมาแล้ว

หน้าปฏิทินต้องแสดงชื่อนัดภาษาไทย ซึ่งแปลว่าต้องเลิกทิ้งอักขระนอก ASCII ใน `Text.swift` และเพิ่ม
ฟอนต์ไทยลง firmware แต่ปัญหาจริงไม่ใช่ฟอนต์ — **LVGL 9.2 ไม่มีเอนจินจัดวางสระและวรรณยุกต์**
มันวาดทีละ codepoint เรียงไปทางขวา ไม่มี GPOS ขณะที่ภาษาไทยซ้อนแนวตั้งได้ถึงสี่ชั้นและตำแหน่ง
วรรณยุกต์ขึ้นกับบริบท (เหนือสระบนหรือไม่ · พยัญชนะฐานหางสูงอย่าง ป ฝ ฟ ฬ หรือไม่) คำที่พบบ่อย
ที่สุดอย่าง "ที่" จึงชนกันทันทีถ้าปล่อยให้ LVGL จัดเอง

**daemon เป็นคนเดินคลัสเตอร์และเลือกร่างของ glyph** แล้วส่ง codepoint ที่ประกอบร่างแล้วไปให้
board — วิธีเดียวกับที่ฟอนต์บิตแมปไทยใช้มาตั้งแต่ยุคเครื่องพิมพ์ คือมีวรรณยุกต์หลายร่างที่ระดับ
ความสูงต่างกันแล้วเลือกตามฐาน ผลคือ firmware **ไม่ต้องมีโค้ดใหม่แม้บรรทัดเดียว** ได้แค่ glyph
เพิ่มในฟอนต์ และหลัก "daemon เป็นเจ้าของตรรกะทั้งหมด firmware แค่วาด" ยังอยู่ครบ

ทางเลือกที่ปฏิเสธ: ให้ Mac เรนเดอร์ข้อความเป็นบิตแมปแล้วส่งพิกเซล (สี่บรรทัดกินราว 1.6KB
เกิน MTU สามเท่า และขัด ADR-0004 เพราะ layout ย้ายไปอยู่บนสาย) และการถอดเป็นอักษรโรมัน
(อ่านไม่ออกจริงในทางปฏิบัติ)

## ผลที่ตามมา

- **ตารางการเลือกร่างเป็นข้อมูล ไม่ใช่โค้ด** — อยู่ใน `tools/thai.toml` แล้ว generate เป็นตาราง
  ทั้งฝั่ง Swift และฝั่ง Python เหมือนที่ `layout.toml` generate `layout.h` ส่วนอัลกอริทึมเดินคลัสเตอร์
  พอร์ตสองฝั่งตามแบบแผน `gen/*.py` ↔ `ct_*.c` ที่มีอยู่แล้ว และต้องมีเทสต์ใน `tamatest` กันดริฟต์
- **`preview.py` ต้องใช้ฟอนต์บิตแมปตัวเดียวกับที่แปลงลงบอร์ด ไม่ใช่ TTF ต้นฉบับ** — ถ้าใช้ TTF
  เอนจินของ PIL จะจัดวางได้สวยกว่าบอร์ดจริง แล้วพรีวิวจะกลายเป็นคำโกหกตรงจุดที่ต้องใช้ตัดสินใจ
  ซึ่งขัดกฎ "preview ไม่ตรงกับบอร์ด = บั๊กของ renderer โดยการก่อสร้าง"
- **การนับความยาวข้อความต้องข้ามอักขระที่กว้างศูนย์** สระบนและวรรณยุกต์ไม่กินความกว้าง การนับ
  ตัวอักษรตรงๆ จะตัดข้อความไทยสั้นเกินจริงได้ราว 40% (คำนี้คือ *display width* ใน `CONTEXT.md`)
- ฟอนต์ต้องเป็นสัญญาอนุญาตแบบเปิด (OFL — Noto Sans Thai หรือ Sarabun) แปลงเฉพาะ subset ที่
  12px และ 14px ราว 2KB ต่อขนาด ซึ่งไม่กระทบงบ flash 4MB
